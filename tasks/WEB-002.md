# WEB-002 — High-refresh performance profile

- Status: done
- Owners: Vision (world profiles), Milu (adaptive resolution and measurement)
- Reviewer: Stark

## Scope agreed before implementation
Target approximately 120 Hz on suitable hardware through a bounded Performance
profile, without promising a frame rate or changing Godot. Preserve the chosen
cloud-cover fraction, cloud-bank layout, weather, cockpit and controls. Reduce
raymarch/lighting detail and terrain draw work rather than silently deleting
clouds. Milu owns application integration, adaptive DPR and actual benchmarks.

## Acceptance criteria
- `setQuality('performance')` changes measurable world rendering work.
- High quality retains the existing 80-step cloud profile.
- Active bank count and cloud-cover state remain unchanged by quality switches.
- Profile settings are exposed for benchmark metadata.
- Milu measures browser/GPU timing and visually checks the tradeoffs; no 120 Hz
  achievement claim follows from source changes alone.

## Evidence and outcome
World hotspot inspection: each High cloud step can evaluate full seven-lobe
density four times (main ray plus three optical-shadow samples), with multiscale
erosion noise. Terrain has 512x512 cells, or 524,288 triangles.

Implemented `setQuality('performance')`: 28 main ray steps, one optical-shadow
density sample and broad erosion with a mean fine-noise substitute. Balanced is
40 steps/two shadow samples; High retains 80 steps/three samples and fine erosion.
Balanced and Performance select a cached stride-two terrain index (131,072
triangles), sharing original height/normal/vertex buffers. No bank is removed or
cloud-cover fraction changed by quality. `getPerformanceSettings()` exposes the
actual profile, sample counts, terrain triangles, active banks, cover and weather.

Validation: JavaScript syntax and whitespace checks passed. A one-off Node scene
test exercised all 27 combinations of three weather presets, three cover values
and three quality profiles; active bank counts/cover were preserved, terrain
index counts matched metadata, and disposal removed the world from the scene.
Milu integrated the default `120 FPS target · Adaptive` profile. Pixel ratio
adapts from at most 1 down to a 0.6 clarity floor against the 8.33 ms target,
preferring asynchronous GPU timers and using active CPU work if unavailable.
The controller waits for GPU warm-up and does not infer overload from a
display-limited rAF callback. High remains full-detail and non-adaptive.

Performance shadow maps use 1024 resolution and redraw up to 30 Hz; High uses
2048/up to 60 Hz. Paused maps are cached; the projection matrix is updated every
frame so shared aircraft/light translation does not detach the cached shadow.
Weather/profile/reset changes invalidate the cache. Telemetry now updates at
5 Hz independently of whether flight is paused, removing repeated DOM rewrites.

Final evidence: `threejs-prototype/artifacts/benchmark-normal.json`, with normal
headless Chrome 156 scheduling, ANGLE/D3D11 on RTX 4060 Ti. Nine-second sampled
flying windows followed warm-up; raw timing samples are counted once. The
benchmark avoids per-frame percentile sorting/state cloning. CPU active work is
not total browser time and overlaps GPU work, so the two must not be added.

| Viewport / profile | Pixel ratio | GPU mean | GPU p95 | GPU samples over 8.33 ms | Observed headless FPS |
| --- | --- | --- | --- | --- | --- |
| 1920x1080 / High | 1.0 | 17.14 ms | 27.20 ms | 100% | 57.75 |
| 1920x1080 / Performance | 1.0 | 6.91 ms | 8.77 ms | 5.56% | 100.00 |
| 3840x2160 / Performance | 0.6 | 9.88 ms | 13.75 ms | 76.26% | 97.56 |

The last case internally renders at 2304x1296, not native 4K. It still misses the
budget at the clarity floor. Normal headless scheduling near 100 FPS is not
physical-screen 120 Hz proof. An uncapped diagnostic is separately recorded in
`benchmark-uncapped.json`; its flags do not alter the application's normal loop.
It used an earlier, slower adaptive-response threshold; do not mix its 4K result
with the final normal-scheduling run or treat uncapped throughput as display FPS.

Twenty-two browser integration checks, six render-budget checks and the production
build passed. Build retains the known nonblocking large-bundle warning. Stark
inspected actual High/Performance screenshots: cockpit, cloud coverage and
landmarks are preserved, with softer clouds, more contour banding and coarser
terrain in Performance. No new shader/browser errors were recorded.

Completed scope: a measurable, reversible 120-target profile and measurement
tooling. Native sustained 120 Hz is explicitly unverified and not marked achieved;
120 Hz-capable hardware/display/browser testing, spikes and 4K optimization remain.

## Stark final independent review — 2026-11-01

Verdict: approve the bounded **120 FPS target profile**, adaptive resolution and
measurement work. Sustained native 120 Hz has **not** been demonstrated. No
blocking source issue was found in the reviewed final implementation.

Reviewed `src/render-budget.js`, the integration/shadow scheduling in main.js,
the benchmark sampling path, actual High/Performance 1920x1080 images and
`artifacts/benchmark-normal.json`. The final verification artifact lists 22
passing checks and no errors, including default adaptive mode, reversible High
detail, cloud-cover preservation and existing controls. Six controller checks
were reported by Milu; Stark's independent work is source, image and evidence
review rather than a duplicate execution of every automated check.

Implementation assessment:
- Performance retains six active banks at the benchmark's 45% cover while
  reducing cloud steps 80 to 28, optical-shadow samples three to one, and terrain
  triangles 524288 to 131072. High remains available.
- Adaptive resolution uses asynchronous GPU timers when available and waits for
  samples instead of treating display-paced callback intervals as GPU work.
  Its 0.6 scale floor preserves a bounded clarity limit; it cannot ensure the
  budget on hardware/workloads that remain too slow at that floor.
- Shadow redraws are cached while the light projection still follows rig
  translation each frame. Telemetry updates are throttled. The initial CPU/GPU
  rolling-average resampling and heavy per-frame benchmark snapshots were
  corrected to once-collected raw timings and a cheap scalar resolution query.
- CPU active update/render time and GPU draw time overlap; adding them would be
  incorrect. The CPU timer is not a whole-browser/compositor frame measurement.

Final normal headless evidence, local RTX 4060 Ti / ANGLE D3D11 / Chrome 156:

| Workload | Internal resolution | GPU mean | GPU p95 | GPU samples above 8.33 ms |
| --- | --- | --- | --- | --- |
| High, 1080p viewport | 1920x1080 | 17.14 ms | 27.20 ms | 100% |
| Performance, 1080p viewport | 1920x1080 | 6.91 ms | 8.77 ms | 5.56% |
| Performance, 4K viewport at scale 0.6 | 2304x1296 | 9.88 ms | 13.75 ms | 76.26% |

The 1080p profile substantially reduces measured draw cost, but its p95 exceeds
8.33 ms. Normal headless callbacks averaged approximately 58 FPS for High and
100 FPS for Performance; neither is evidence of physical display refresh.
The 4K viewport case is internally reduced resolution and still exceeds the
budget on average, so it does not support a native 4K/120 claim. Uncapped runs
explicitly disable scheduling limits and are throughput diagnostics only.

Visual assessment: cockpit, displays, UI, river and principal landscape features
remain intact in the Performance still. Cloud bodies become smoother/flatter,
with visible contour bands in the large left cluster; distant ridges change
with the coarser terrain index. These are acceptable, reversible profile
tradeoffs rather than visually identical output. Motion shimmer and shadow
update cadence require an interactive target-display assessment.

Evidence limits: runs are short local flying samples rather than repeated
thermal-steady benchmarks over multiple weather/cover/camera workloads. A native
120 Hz browser/display session was not available for verification. Six-sample
adaptation is an initial responsiveness heuristic, not a sustained-frame-time
guarantee. Keep the UI and user-facing report phrased as a target with measured
improvement and explicit remaining misses, not achievement of locked 120 FPS.
